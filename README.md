Companion Code for Rust high load Grimoire.

This repository contains the working code for every chapter of Rust Data-Intensive Grimoire
- a hands-on guide to Rust built around a single artifact, that grows from an empty project into a REST API,
persistence, logging, and integration and performance tests.

## About

This is mini-Twitter built as an educational high-load service running in Kubernetes.
Traffic grows gradually and a 2–5 minute pod startup is acceptable, so scaling relies on
autoscaling with headroom rather than instant bursts.

## Approach

Metrics come first. Every iteration follows the same loop:

1. Implement a feature the simple way.
2. Load it with k6 and find the problem on the dashboard.
3. Apply a fix and add a metric that proves it works.
4. Compare before/after on the same dashboard.

## Scope

- No login/registration: JWTs are generated by a CLI utility and validated by the service
  (`sub` = user id, user is upserted on first request).
- API:
  - `POST /tweets` — publish a tweet
  - `POST /follow/{id}`, `DELETE /follow/{id}` — follow/unfollow
  - `GET /timeline` — home timeline
  - `GET /users/{id}/tweets` — user's tweets

## Roadmap

**Step 0 — foundation**

- `/metrics` endpoint in Prometheus format
- RED metrics per endpoint: rate, errors, duration histogram
- Local VictoriaMetrics (vmagent + single-node) + Grafana
- Baseline k6 scenario

**Iterations**

| # | Problem on the dashboard | Solution | Key metric |
|---|---|---|---|
| 1 | Timeline via SQL, p99 grows | Indexes, cursor pagination | p99 latency, DB query time |
| 2 | DB connection pool exhausted | Pool tuning, PgBouncer | pool wait time, active connections |
| 3 | Repeated reads hammer the DB | Redis cache | cache hit ratio |
| 4 | Timeline is still expensive | Fan-out on write + worker | queue length, fan-out lag |
| 5 | Celebrity with 1M followers breaks the queue | Hybrid fan-out | job processing time, backlog |
| 6 | One pod is not enough | HPA + KEDA | replicas vs RPS |
| 7 | RSS grows under load, OOMKills, uneven memory on scale up/down | jemalloc/mimalloc, `MALLOC_ARENA_MAX`, decay tuning, tokio workers vs CPU limit | RSS vs allocated, fragmentation, OOMKill count |
| 8 | Errors during deploy / scale-down | Probes, graceful shutdown | 5xx during rollout |
| 9 | Slow dependency takes everything down | Timeouts, circuit breaker, rate limit | breaker state, rejected requests |

## Conventions

- Fixed k6 profiles (ramp, spike, soak) for fair comparisons
- One shared Grafana dashboard with deploy annotations
- A git tag per iteration to reproduce any stage
